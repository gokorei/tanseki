# Project governance

This document describes how Tanseki is governed. It is the authority on
contribution policy; where it and any other file disagree, this file wins.

## Status: read-only

**Tanseki is published read-only. External code contributions are not accepted.**

The repository, its issues, and its pull requests are public, but the
maintainer does not merge changes proposed by others. This is a capacity
decision, not a judgment about any individual contribution or about the people
who would make one. The practical consequences:

- Pull requests are not merged, including bug-fix pull requests and one-line
  typo corrections. A pull request template in `.github/` states this at the
  moment a contributor opens one.
- Pull requests are still *opened*: they are a way to share a patch, and are
  closed rather than ignored. Treat a closed pull request as "not now, and not
  by me", not as a review of the idea.
- Issues are read and triaged on a best-effort basis. There is no response-time
  commitment, and no guarantee that any reported issue will be fixed.
- Discussions, questions, and feature requests are not answered.
- Security reports **are** received and acted on. See
  [SECURITY.md](SECURITY.md); the read-only rule explicitly does not apply to
  private vulnerability reports.

If you need Tanseki to change, the reliable path is to fork it. Apache-2.0 is
chosen precisely so that the fork needs no permission from anyone.

## What you may do with this repository

Everything the license allows, with no further permission and no obligation to
ask. In particular you may:

- read, study, and run the code;
- fork it, and publish your fork under any terms you choose, including
  proprietary ones;
- redistribute it, including commercially;
- modify it and use the result internally;
- submit patches by email or pull request to the maintainer, understanding that
  they will not be merged by this repository.

You may use the name "Tanseki" to refer to the unmodified project. See
[Trademarks](#trademarks).

## No CLA, and why

There is no CLA, and no Developer Certificate of Origin, and no inbound=outbound
sign-off requirement. Contributors are asked for neither on any channel.

This is a consequence of the read-only rule, not an oversight. A CLA exists to
grant the project rights in contributed code. Since the project does not accept
external code, there is nothing for a CLA to cover. Copyright in what you write
stays entirely yours, and in a fork you publish it stays yours.

The corollary is that no third-party code is present in this repository. See
[Third-party code](#third-party-code).

## Decision making

One maintainer holds all decision rights: technical direction, the wire
contract, schema and migration policy, what lands on `main`, and when. There is
no voting, no review quorum, and no second maintainer to break a tie.

When that maintainer cannot be reached or the project is inactive, the project
does not fall back to a foundation, a steering committee, or a benevolent
dictatorship-in-waiting. It simply stops. Treat the absence of recent activity
as the answer.

## Changing this policy

This policy can change, in either direction, by the maintainer changing this
file. If the project ever begins accepting contributions, this file will be
updated **first**, before the tooling changes, and it will state the CLA
position, the review process, and who participates in it.

Nothing here restricts the maintainer's freedom to license, relicense,
trademark, publish, or unpublish the work. Apache-2.0 includes an explicit
patent grant and an express disclaimer of warranty; read
[LICENSE](LICENSE) for what it does and does not promise.

## Trademarks

Apache-2.0 grants copyright and patent rights. It does not grant trademark
rights. "Tanseki" and the Tanseki logo are not licensed by
[LICENSE](LICENSE). Use of the name to refer to the unmodified upstream project
is fine; do not use it in a way that suggests the maintainer endorses your fork
or your product.

## Third-party code

The repository contains no vendored third-party source. Dependencies are
resolved at build time from Maven Central, crates.io, and PyPI, are pinned
through `gradle/verification-metadata.xml` and hash-pinned requirement files,
and carry their own upstream licenses, which apply to them and not to Tanseki.

Two files are generated by [OpenAPI Generator](https://openapi-generator.tech)
and are not hand-written Tanseki work: `sdk/generated/**` and the export of
`docs/openapi.json`. They are Apache-2.0 as well, and remain machine-generated
across regeneration. Their provenance and regeneration policy are covered by
`CONTRIBUTING.md` and enforced by the `checkOpenApiAndSdkDrift` gate.

Tanseki's own license is Apache-2.0, with `Copyright 2026 The Tanseki Authors` in
[LICENSE](LICENSE).

## Enforcement

Maintainers of this project are not required to follow
[CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) when interacting with each other, but
they are bound by it when interacting with anyone else in the project's spaces,
including a repository under another owner's control that carries this project
in its name.

See also: [CONTRIBUTING.md](CONTRIBUTING.md), [SECURITY.md](SECURITY.md).
